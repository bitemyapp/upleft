# Known differences from Downright

This ledger lists every place where Upleft is known or suspected to behave differently from the Swift original. An entry leaves this file only when its difference is fixed and a conformance case covers it, or when the entry is recorded as an intentional, reviewed deviation.

## Open

| Area | Difference | Found by | Plan |
|---|---|---|---|
| Theme JSON decoding (`upleft-render` `swift_compat`) | Swift's `JSONDecoder` rejects some zero literals, such as `0e1` and `0.00e-5`, and the port accepts them. This only affects malformed theme files. | render-base port | Find Foundation's number grammar with a probe covering every literal shape, then match it. Add a malformed-theme corpus to the `vscode-theme` suite. |
| `upleft-math` `add_latex_symbol` across threads | The symbol table stores the registered atom itself, as Swift does, so a later change to it shows in lookups on the thread that registered it. Another thread gets a copy of the atom as it was when registered, because Rust can't share the caller's non-thread-safe cells. In Swift that cross-thread read is a data race unless the caller synchronises. Downright never calls `add(latexSymbol:)`. | math-variants | Keep. Covered by `crates/math/tests/add_latex_symbol_tests.rs`. |
| `.drBlock` and `.drPathToken` values (`upleft-render` `swift_value`) | Swift stores `BlockIdentity` and `PathToken` in `__SwiftValue` boxes; the port uses the NSObject subclasses `UpleftBlockIdentityValue` and `UpleftPathTokenValue`. `isEqual:` matches Swift's `Hashable` equality, so attribute runs coalesce identically (decorate 5454/5454), but the class names, `-description` and `-hash` values differ. | engine port | Keep unless something reads the class name. |
| Lone surrogates in the decoration engine | Swift reads a code block's text and a callout's source through `String`, which repairs a lone surrogate to U+FFFD before highlighting or searching; the port passes the UTF-16 units as they are. Unverified; no corpus document has a lone surrogate. | engine port | Add a lone-surrogate document to the corpus and compare. |
| `ClipboardSemanticHTML` substring search | Swift's `Substring.range(of:)` is Foundation's non-literal search; the port matches Character by Character, with Swift's canonical equivalence for single characters. The two agree on the corpus (clipboard 909/909). Unverified next to composed sequences such as `*` followed by a combining mark. | engine port | Add clipboard cases with combining marks after `*`, `_`, `~` and backticks. |
| `DecorationResult.elapsed` | Measured with a monotonic clock; Swift subtracts `CFAbsoluteTimeGetCurrent()` readings, which follow wall-clock changes. Only the timing differs. | engine port | Intentional. |
| ELK layering where elk-swift is nondeterministic (`upleft-elk`) | elk-swift iterates `NetworkSimplex.treeEdges`, a `Set` hashed by object address with a per-process seed, and breaks `HyperEdgeCycleDetector` ties the same way, so on some graphs its layout varies from run to run. None of the graphs captured from real Mermaid diagrams vary; 50 of the 449 corpus graphs (random and polyline stress graphs) do. Upleft always takes the insertion-order outcome. On 37 of the 50 that equals one of 16 sampled elk-swift runs. On 13 it equals only the instrumented elk-swift copy (`just elklab`), and whether plain elk-swift can produce those outcomes is unverified. The `elk` oracle emits `{"alternatives": [...]}` only for graphs whose samples disagree, and consults the instrumented copy only then. | elk port | Keep. Downright has no single output to match on these graphs. Watch for any Mermaid-derived graph that varies. |
| ELK compound preprocessor | The port clears the port-to-node entry list at the start of every layout; Swift never clears it. The stale entries only touch graphs from earlier layouts, so the output is identical. | elk port | Keep. |
| `DocumentHealth` footnote order | Swift walks footnotes in `Dictionary` order, which changes from run to run; the port walks them by position. No real parse can show the difference. | core port | Keep. Swift has no fixed order to match. |
| Atomic save temp names | Foundation's `.sb-` temp-file naming is only approximated, and its fallback for a directory that isn't writable is not ported. | core port | Port the naming exactly when the app layer lands. Check by saving into a directory that isn't writable. |
| Sorting by Swift `String <` (`upleft-swift-text` `str_cmp`) | Swift's `<` is not a strict weak order on strings that are not in NFC: when one string's NFC is a prefix of the other's, the string with fewer UTF-8 bytes is less, so `"a\u{301}"` and `"\u{E1}b"` are neither less nor equal. `str_less` reproduces `<` exactly (the `unicode` suite checks it), but Rust's `sort_by` over `str_cmp` can order such keys differently from Swift's sort, or panic where Rust detects the inconsistency. Real keys (link labels, identifiers, theme names) do not hit this. | swift-text | Port Swift's `sort(by:)` (its insertion sort and merge) into `upleft-swift-text` and use it wherever a port sorts by a `String` comparison. |
| `String` comparison on bridged strings | `str_less` models native Swift strings. A string bridged from an `NSString` skips the byte-prefix shortcut and compares remaining lengths in UTF-16 units, so the same two strings can order differently when one side is bridged. Not observed in any port. | swift-text | Add a `str_less_bridged` when a call site is found that compares a bridged string with `<`. |
| `ThemeStore` hot reload | Rust reads the themes folder on a background queue during a hot reload. Swift reads it on the main thread. The loaded result is the same; only when it lands can differ. | render-base port | Intentional, per AGENTS.md: never block the main thread. The observable state after a reload must still match. |
| Sequence diagrams: open activations (`upleft-mermaid` `src_sequence_layout`) | Activations still open after the last message are appended in Swift `Dictionary` order, which is randomised per process, so Swift's own order varies between runs. Upleft appends them in first-activation order. Bars of different participants never overlap, so pixels are unaffected. The `mermaid-layout` dump compares activations sorted. | mermaid port | Intentional: Swift has no stable order to match. |
| `String.contains` provenance (`upleft-mermaid` `swift::contains`) | Swift's `contains` is Character-wise on a native string but Foundation's search on one bridged from an `NSString` (see `upleft-swift-text` `contains_bridged`). beautiful-mermaid makes many labels through `NSRegularExpression` and `NSString.substring`, so some are probably bridged. The port always searches Character-wise. The two can only disagree on a label where `\n`, `$` or `*` sits inside a grapheme cluster (for example `\r` then `<br>` in a flowchart label, giving `\r\n`). No corpus diagram does. | mermaid port | Probe the provenance of each `contains` call site's receiver with the corpus's adversarial labels and switch those sites to `contains_bridged`. |
| Sparkle not linked (`upleft-app` `updater::update_engine`) | `SparkleUpdateEngine` and `DownrightUpdateDriver` are ported against seams (`SpuUpdater`, `SuAppcastItem`, the Sparkle value types) because Sparkle arrives with app packaging. Until something calls `set_spu_updater_factory`, `SparkleUpdateEngine::new` answers `None` even for a valid Info.plist, so `UpdateCoordinator::start` leaves the updater in its ordinary disabled state; Downright would build the engine. The driver is not yet an Objective-C `SPUUserDriver`. | updater port | Link Sparkle 2.9.6 with packaging: implement `SpuUpdater` over `SPUUpdater`, install the factory, and declare the `SPUUserDriver`/`SPUUpdaterDelegate` classes that forward to `DownrightUpdateDriver` and `BackgroundDownloadNotifier`. |
| Feed probe threading (`upleft-app` `updater::release_watch`) | `ReleaseFeedURLProbe` classifies the response and hashes the body (up to 4 MiB of SHA-256) on the `URLSession` delegate queue, then hops to the main queue with the answer; Swift does both after resuming on the main actor. The answer and the order of main-queue work are the same (`updater` suite, `feed-probe*`). | updater port | Intentional, per AGENTS.md: never block the main thread. |
| `stateDidChange` object (`upleft-app` `updater::update_coordinator`) | Swift posts `Downright.UpdateCoordinator.stateDidChange` with the coordinator as `object`. The port's coordinator is not an Objective-C object, so it posts a per-coordinator `NSObject` stand-in, `notification_object()`; observers that filter by object must pass that. Name, timing and count of posts are identical (`updater` suite). | updater port | Keep; the UI port observes with `notification_object()`. |
| Update panel (`upleft-app` `updater::update_coordinator`) | `showPanel()`/`closePanel()` reach `UpdateWindowController` through the `UpdatePanelController` factory seam. Until the UI port installs a factory they only count (`panel_show_count`), as they do in Swift under `suppressUIForTesting`. | updater port | The UI port implements `UpdatePanelController` over its window controller and calls `set_panel_factory`. |
| Background-download callback from another thread (`upleft-app` `updater::update_coordinator`) | Swift's `onBackgroundDownloadCompleted` hops to the main actor when Sparkle calls it off the main thread. The port's handler is not `Send`, so it can only be invoked on the coordinator's thread and calls straight through; the Sparkle delegate bridge must deliver on the main thread. | updater port | Handle the hop in the `SPUUpdaterDelegate` bridge when Sparkle is linked. |
| Release watch system events (`upleft-app` `updater::release_watch`) | `observeSystemEvents` (activation, power-state and wake notifications, `NWPathMonitor` through Network.framework's C API) is ported but unverified: neither the Swift tests nor the `updater` suite start a watch with system events, since their timing is live. | updater port | Verify in the running app once the UI port starts the coordinator: toggle activation, Low Power Mode, sleep/wake and Wi-Fi and compare probe counts with Downright. |
| Canonically equivalent keys in agent settings (`upleft-cli` `agent_bridge::bridged`) | `down hook --install`/`--uninstall` and `AgentIntegration` bridge a parsed `settings.json` object to a Swift `[String: Any]`, which merges keys that differ only in Unicode normalization (`"é"` and `"e\u{301}"`, `"K"` and KELVIN SIGN) into one entry. Which entry survives changes from process to process in Swift (probed: two runs of the same program disagree; it follows the per-process hash seed). Upleft keeps the last one in `NSDictionary` enumeration order. Nested objects the code never casts keep every key on both sides; the `down-cli` suite checks that (`hook-install-nested-canonical-duplicate-keys`). | cli port | Keep. Swift has no stable result to match. |
| `down` launch paths (`upleft-cli` `bin/down`) | The paths that start Downright or Finder are not in any conformance suite, because running them would launch an app: `open` and `notify` success (`locateApp`, `mdfind`, the `/usr/bin/open` arguments), `--reveal` success (`NSWorkspace.activateFileViewerSelecting`), `watch` success (FSEvents to `open`), and "could not find Downright.app" (depends on what `mdfind` finds on the machine). Ported line by line and unverified; `AgentWatcher`'s stream is covered by a Rust test that records instead of launching. | cli port | Add an injection point for the launcher if Downright grows one; until then, review by hand. |
| `down doctor` results depend on the machine | `codesign`, `spctl`, `xcrun stapler`, `pluginkit` and the default `.md` application are read from the machine, as in Swift. The `down-cli` suite caches Swift's result per scenario, so a change on the machine (a Downright.app installed in /Applications, a new Quick Look registration, another default Markdown app) makes the cached Swift results stale. | cli port | Rerun with `--no-cache` after such a change. |
| `KeybindingStore` persistence (`upleft-app` `support::keybindings`) | Swift writes `keybindings.json` synchronously from the thread that edits the store (the main thread, in Settings). The port encodes the bytes synchronously and writes them on a private serial queue, so `lastPersistenceError` is updated when the write finishes (`flush()` waits for it). The file is byte-identical (palette suite, 11 store cases). The store is a `Mutex`-guarded singleton, so its first load can run off the main thread. | palette port | Intentional, per AGENTS.md: never block the main thread on `fsync`. |
| `KeybindingLoad.decode` error choice (`upleft-foundation` `json_decoder`) | Swift decodes the entries of `[String: [KeyBinding]]` in per-process hash order, so when two entries would throw different errors (`keyNotFound`/`valueNotFound` 4865 vs. `dataCorrupted`/`typeMismatch` 4864), Swift reports either one and the user sees one of two messages. The port walks document order. Likewise, two override names that are canonically equivalent (`showKeybindings`, `show\u{212A}eybindings`) resolve to one command, and which binding list wins follows hash order in Swift and document order in the port. | palette port (probe) | Keep: Swift has no stable order to match. The palette corpus avoids such files. |
| `KeybindingStore.lastPersistenceError` | Held as the write error's text (`io::Error`), not an `NSError`; only its presence is observable (nothing in Downright displays it). | palette port | Keep unless a caller starts showing it. |
| Main-actor callbacks in `SystemIntegration`, `SpeechCoordinator`, `IntegrationRegistry` | Swift's `@MainActor` isolation becomes a `MainThreadMarker` parameter; completions (`registerWithSystem`, `makeDefaultMarkdownHandler`, `moveToApplications`' relaunch failure) are delivered on the main queue, as Swift's `DispatchQueue.main.async` / main-actor resumption delivers them. `makeDefaultMarkdownHandler` takes a completion instead of being `async`. Not exercised by a conformance suite (they change system state). | palette port | Keep; the UI port wires them. Unverified beyond compile and the `main_thread_objects` test. |
| `FileWatcher` rename search (`upleft-app` `ai::file_watcher` `locate`) | When the watched file disappears, the port looks for its inode among the directory's entries and skips any entry whose name is not valid UTF-8. Swift's `FileManager.contentsOfDirectory(atPath:)` returns such names in a decoded form. APFS and HFS+ only store valid Unicode names, so this can only matter on foreign volumes (SMB, FAT), and only when the renamed file itself has such a name. Unverified. | document port | Probe `contentsOfDirectory(atPath:)` on a volume that allows arbitrary bytes, then match its decoding. |
| Save-failure text (`upleft-app` `ai::markdown_document` `DocumentError`) | When a read, encode or write inside `MarkdownDocument` fails with a filesystem error, the `saveFailed` presentation detail, the `onSaveFailure` error and `SaveError.fileUnreadable`'s description show the Rust `io::Error` text (for example "No such file or directory (os error 2)"). Swift shows Foundation's `localizedDescription` ("The file “x.md” couldn’t be opened because there is no such file."). `DocumentIOError`, `PosixError` and `CocoaError(.fileNoSuchFile)` ("The file doesn’t exist.") already match. | document port | Map `io::Error` kinds to Foundation's `NSCocoaErrorDomain` file-error descriptions in `upleft-core` `document_io`, probing each code. |
| Parse control order on open (`upleft-app` `ai::markdown_document`) | Swift sends the coordinator's `resume`/`discardPending` through a chain of `Task`s, while the first-paint `runImmediately` comes from a separate detached task, so the two race and a reopened document can occasionally see its first priority parse refused as "suspended". The port sends all of these through the coordinator's FIFO queue in call order, so `resume` always lands first. | document port | Keep: Swift has no fixed order to match. |
| Persisted JSON key order (`upleft-app` `snapshot_store`, `document_state_store`, `reader_profiles`) | Snapshot indexes, state files, `recents.json` and the custom reader-profile file are written by a `JSONEncoder` without `.sortedKeys`, whose key order changes from process to process in Swift. The port writes `CodingKeys` order. The `formats` suite compares these files parsed. | app-persist port | Keep. Swift has no stable order to match. |
| `Set` member order in persisted files (`upleft-app` `document_state_store`, `trust_store`) | Swift writes `foldedHeadings`, `expandedCodeBlocks`, `collapsedCodeBlocks` and each grant's `effects` in per-process hash order. The port writes strings sorted by UTF-8 bytes, offsets ascending, effects in declaration order. `foldedHeadings` keeps Swift's set semantics (`StringSet`: canonically equivalent slugs are one member, the first spelling wins). | app-persist port | Keep. The `formats` suite sorts these members on both sides. |
| `SnapshotStore.waitForPendingWrites()` / `pruneOneGenerationForTesting()` (`upleft-app` `snapshot_store`) | Swift's are `async`; the port's block the caller until the history queue drains. `after_pending_writes` is the non-blocking form. | app-persist port | Intentional. Never call the blocking forms on the main thread. |
| `Preferences` load, recovery and persistence (`upleft-app` `preferences`) | Not covered by the `formats` suite: `Preferences.shared` is the only Swift entry to `read(contentsOf:)` and `persist()`, and it writes the user's global preferences (`PreviewAppearanceStore`), which `CFFIXED_USER_HOME` does not isolate. The suite checks `Preferences.Values` decoding and encoding byte for byte; the load path is covered by Rust tests only (`tests/preferences_load_tests.rs`). Unverified against Swift. | app-persist port | Cover it if the app oracle ever gets an isolated preferences domain. |
| `ChangeTracker` threading (`upleft-app` `change_tracker`) | The tracker holds `Rc` state and its fade timer runs on the main run loop, so it must live on the main thread; Swift's class can be created anywhere (its timer also fires on the main run loop). | app-persist port | Keep; MarkdownDocument owns it on the main thread. |
| `Date.iso8601` before Julian Day 0 (`upleft-foundation` `date`) | Dates before -4712-01-01T12:00:00Z print as that instant, as Swift printed a single probed point (-3e11 s). Other points are unverified. | app-persist port | Probe a range if a caller ever writes such dates. |
| `ExternalEditor.open` (`upleft-app` `path_resolver`) | Ported call for call (NSWorkspace, `Process`, `NSAppleScript`), but its side effects (launching editors, Terminal) are not exercised by any test or suite. Unverified. | app-persist port | Cover with the UI port's window-level checks. |

## Reproduced on purpose

These are Downright behaviours that look like bugs. Upleft reproduces them because pixel-exactness requires it.

| Behaviour | Where |
|---|---|
| `SmartPaste.plainText(forHTML:)` never returns on input such as `a < b`. The port reproduces the hang. | `upleft-core` SmartPaste |
| swift-markdown measures every table row as the width of the first row when it pads column alignments. cmark never produces rows of different widths, so real input is unaffected. | `upleft-markup` tables |
| An xychart whose values or range approach `1e300` overflows its nice ticks to infinity, and the renderer's `Int((xBase / 20).rounded())` traps: Downright crashes on such a fence. Upleft panics at the same point. The two inputs live in `corpus/mermaid-traps/` (read by no suite); a test checks the panic. | `upleft-mermaid` `diagram_renderer_xy_chart` |
| beautiful-mermaid's flowchart clipping compares shapes against `"stateStart"`/`"stateEnd"`/`"stateFork"`, but positioned nodes carry `"state-start"`/`"state-end"`, so edges into start and end states are clipped as ellipses. | `upleft-mermaid` `src_layout` |
| After shifting a flowchart right or down to fit an edge label, only the top-level subgroup rectangles move; nested subgraph rectangles keep their old coordinates. | `upleft-mermaid` `src_layout` |
| `BMColor(hex:)` treats any length other than 6 or 8 hex digits as opaque black, so `style A fill:#f9f` and named colours such as `red` fill black. | `upleft-mermaid` `cross_platform` |
| `down export` traps (`SIGTRAP`, no message) on an image whose percent-decoded source leaves nothing before the query once split at `#`, such as `![x](#)`, `![x](?)`, `![x](?#b)` or `![x](\t)`: `imageSourceIsSafe` indexes `[0]` into an empty `split` result. Upleft traps the same way (`brk #1`). The `down-cli` suite covers it (`export-image-fragment-crash`). | `upleft-cli` `markdown_cli` |
| `KeyBinding.key(for:)` never produces `"backslash"`: it lowercases the event's characters, so ⌘\\ arrives as `"\\"` and misses the default Split View binding (`KeyBinding("backslash", .command)`). The chord works only through the menu item's key equivalent. The palette suite's store cases check the miss. | `upleft-app` `support::commands`, `support::keybindings` |
| Copies of `CommandPaletteModel` share one result cache (the Swift struct holds a class instance), so a copy can be handed results cached by another copy for the same query. `Clone` shares the cache the same way. | `upleft-app` `support::command_palette_model` |
| A save issued in the same main-queue turn as an edit leaves `MarkdownDocument` dirty again: the edit's `NSTextStorageDelegate` callback runs a turn later, finds the parsed tree still older than the buffer, and calls `setDirty(true)`. In the app a save normally comes turns after the keystroke, so this only shows when code edits and saves back to back. Worked out from MarkdownDocument.swift; not checked with a Swift probe. | `upleft-app` `ai::markdown_document` |

## Retracted

- **"Downright clips the text column on first open."** This was never Downright's behaviour. It came from SwiftPM stamping the binary `sdk 14.0`, which put AppKit into an older compatibility mode. With the canonical build version (docs/BUILD-VERSION.md), the text view takes its full width.
